# MSRPO Chat — переписки, группы и каналы

Java 21, Spring Boot 4.0.8, Spring Security, PostgreSQL, Flyway и Elasticsearch. Один REST API для веб-, мобильного и десктопного клиентов. Новые сообщения приходят по SSE.

Проект включает регистрацию и вход, редактирование профиля и аватара, поиск собеседника по логину, личные диалоги, групповые чаты, публичные каналы с подписками, текстовые сообщения, вложения, историю и поиск по тексту сообщений. Веб-клиент на React и TypeScript находится в `frontend/`, десктопное приложение Electron — в `desktop/`, нативное мобильное приложение React Native с Expo — в `mobile/`.

## Границы текущего этапа по ТЗ

Из перечисленных в учебном задании технологий выбраны Java / Spring Boot, React, Electron, React Native, PostgreSQL и Elasticsearch. Клиенты показывают личные чаты, группы и каналы, сообщения и медиа, общий поиск и меню действий в стиле Minecraft. Для групп и каналов сервер проверяет роль при отправке и удалении сообщений.

Electron переиспользует веб-интерфейс в отдельном приложении; мобильный клиент использует нативные компоненты React Native. Для локальной инфраструктуры есть Docker Compose с backend, PostgreSQL и Elasticsearch; общее развёртывание и настройка среды на другом компьютере выполняются отдельно.

Текущий этап сосредоточен на разработке MVP без отдельного QA по запросу пользователя.

## Десктопное и мобильное приложения

Исходники и инструкции находятся в [desktop/README.md](desktop/README.md) и [mobile/README.md](mobile/README.md). Electron использует тот же интерфейс и функции, что и веб-клиент. React Native содержит отдельные экраны списка и переписки, нижнюю навигацию, меню, поиск людей и каналов, создание групп и каналов, управление ролями и работу с вложениями. Фото и видео отображаются внутри сообщений.

Все три клиента обращаются к одному backend. Адрес API задаётся отдельно для каждого приложения; серверные пароли и JWT-ключ в клиент не передаются. Access-токен хранится только в памяти, поэтому после перезапуска приложения требуется вход.

Docker Compose по умолчанию публикует backend только на `127.0.0.1:8080`. Для Expo Go на Android-телефоне в той же Wi-Fi сети задайте в корневом `.env` `BACKEND_HOST=<IPv4-адрес компьютера>` и в `mobile/.env` `EXPO_PUBLIC_API_URL=http://<IPv4-адрес компьютера>:8080/api/v1`, затем пересоздайте backend командой `docker compose up -d --no-deps --force-recreate backend` и перезапустите Metro. Брандмауэр Windows должен разрешать входящие подключения к TCP 8080 из этой локальной сети. Для Android-эмулятора используйте `http://10.0.2.2:8080/api/v1`. Для Android-устройства, подключённого по USB с включённой отладкой, выполните `adb reverse tcp:8080 tcp:8080` и укажите `http://127.0.0.1:8080/api/v1`. Подключение к Metro для загрузки мобильного приложения настраивается отдельно по инструкции мобильного клиента. Для устройства iOS нужен доступный с него HTTPS-адрес API; локальная сборка iOS требует macOS и Xcode.

Клиенты добавляются как исходники MVP. Зависимости новых приложений, сборки, установщики и работа на устройствах в этом этапе не проверяются; подробные ограничения указаны в их README. База знаний `knowledge/` временно не обновляется по запросу пользователя и может отставать от кода.

## Запуск веб-клиента

После запуска бэкенда откройте второй терминал. Нужны поддерживаемая LTS-версия Node.js, совместимая с Vite 8, и pnpm версии из `frontend/package.json`:

```powershell
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Откройте http://localhost:5173. Этот адрес разрешён настройками CORS бэкенда по умолчанию. Vite направляет `/api` на адрес `BACKEND_HOST` из корневого `.env` и порт `8080`; после изменения адреса перезапустите Vite. На широком экране слева расположена навигация, рядом список с общим поиском людей и каналов, справа выбранная переписка. Создание группы и канала доступно через меню. На телефоне список и переписка открываются отдельными экранами, основные разделы доступны через нижнюю навигацию. Настройки и команды описаны в [README веб-клиента](frontend/README.md).

Access-токен хранится только в памяти: после перезагрузки страницы или истечения сеанса нужно войти снова. Для рабочего развёртывания соберите клиент командой `pnpm build`, настройте HTTPS и проксирование `/api` к бэкенду; Vite предназначен для разработки.

## Запуск через Docker

Для ручного размещения веб-клиента и backend с PostgreSQL и Elasticsearch на Ubuntu VM используйте [инструкцию серверного деплоя](deploy/README.md) и отдельный `compose.prod.yaml`. Автоматический деплой из GitHub пока не подключён.

Нужен запущенный Docker Desktop в режиме Linux containers. Из корня проекта в PowerShell:

```powershell
.\scripts\init-env.ps1
docker compose up -d --build
docker compose logs -f backend
```

Скрипт создаёт `.env` со случайными паролем БД и ключом JWT, если файла ещё нет. Существующий `.env` не перезаписывается и исключён из Git.

- API: http://localhost:8080/api/v1
- Swagger UI: http://localhost:8080/swagger-ui/index.html
- OpenAPI JSON: http://localhost:8080/v3/api-docs

В Swagger зарегистрируйте пользователя, скопируйте `accessToken`, нажмите **Authorize** и вставьте токен. Swagger не сохраняет его между перезагрузками.

Остановка: `docker compose down`. Данные БД, файлы и поисковый индекс сохраняются в Docker volumes. Конфигурация Compose предназначена для локальной разработки: по умолчанию порты доступны только на localhost; при настройке `BACKEND_HOST` API становится доступен по выбранному локальному адресу. Elasticsearch внутри локального окружения без авторизации. Для публичного развёртывания нужны HTTPS, закрытая инфраструктурная сеть и ограничение частоты запросов на входе.

## Запуск Java локально

Установите JDK 21, запустите PostgreSQL и Elasticsearch. В проект добавлен Maven Wrapper; отдельная установка Maven не обязательна:

```powershell
.\scripts\init-env.ps1
docker compose up -d postgres elasticsearch

# Загрузить только переменные из созданного .env, без исполнения содержимого файла.
Get-Content .env | ForEach-Object {
    if ($_ -match '^([A-Z_]+)=(.*)$') {
        [Environment]::SetEnvironmentVariable($matches[1], $matches[2], 'Process')
    }
}
$env:DB_URL = 'jdbc:postgresql://localhost:15432/chat'
$env:ELASTICSEARCH_URL = 'http://localhost:19200'
.\mvnw.cmd spring-boot:run
```

PostgreSQL из Compose доступен на `localhost:15432`, чтобы не конфликтовать с установленным на компьютере PostgreSQL на порту 5432. Внутри Docker используется обычный порт 5432.

Elasticsearch из Compose доступен на `localhost:19200`: порт 9200 может входить в зарезервированный Windows диапазон. Внешний порт можно изменить переменной `ELASTICSEARCH_HOST_PORT` в `.env`; при локальном запуске Java укажите тот же порт в `ELASTICSEARCH_URL`. Внутри Docker backend обращается к `http://elasticsearch:9200`.

При необходимости измените `DB_URL`, `DB_USER`, `DB_PASSWORD`, `ELASTICSEARCH_URL`, `JWT_SECRET`, `CORS_ORIGINS`, `PORT`. `JWT_SECRET` — Base64 от не менее чем 32 случайных байт. `app.jwt.access-ttl` по умолчанию `1h`, допустимо положительное значение не более суток. Смена ключа требует перезапуска и делает старые токены недействительными.

## Контракт API

Для всех запросов, кроме регистрации, входа и документации: `Authorization: Bearer <accessToken>`. Ошибки имеют формат Problem Details (`application/problem+json`). Чужой личный или групповой чат и его файлы возвращают `404`, чтобы не раскрывать их существование. Публичный канал и его вложения доступны для чтения после входа, даже без подписки.

| Метод | Путь после `/api/v1` | Назначение |
|---|---|---|
| POST | `/auth/register` | `{username, displayName, password}` → токен и пользователь |
| POST | `/auth/login` | `{username, password}` → токен и пользователь |
| GET | `/users/me` | Мой профиль, включая приватную дату рождения |
| PUT | `/users/me` | `{displayName, birthDate}` → обновлённый профиль |
| PUT | `/users/me/avatar` | Multipart `file` → загрузить или заменить аватар |
| DELETE | `/users/me/avatar` | Удалить свой аватар |
| GET | `/users/{id}/avatar` | Получить аватар пользователя с авторизацией |
| GET | `/users?q=ali&limit=20` | Поиск логина по префиксу, минимум 2 символа |
| POST | `/conversations` | `{userId}` → новый или существующий диалог, всегда `200` |
| GET | `/conversations?page=0&limit=20` | Мои диалоги с собеседником и последним сообщением |
| POST | `/groups` | `{title, memberIds}` → создать группу, ответ `201` |
| GET | `/groups?page=0&limit=30` | Группы, в которых я состою |
| GET | `/groups/{id}` | Группа, моя роль и число участников |
| GET | `/groups/{id}/members?page=0&limit=100` | Участники и их роли |
| POST | `/groups/{id}/members` | `{userId, role}` → добавить участника с ролью `MEMBER` или `READER` |
| PUT | `/groups/{id}/members/{userId}` | `{role}` → изменить роль участника |
| DELETE | `/groups/{id}/members/{userId}` | Удалить участника или покинуть группу; ответ `204` |
| POST | `/channels` | `{username, title, description}` → создать публичный канал, ответ `201` |
| GET | `/channels?page=0&limit=30` | Каналы, на которые я подписан |
| GET | `/channels/search?q=строй&page=0&limit=30` | Поиск публичных каналов по названию или логину, от 2 символов |
| GET | `/channels/{id}` | Название, описание, владелец и состояние подписки |
| POST | `/channels/{id}/subscription` | Подписаться, ответ с текущими данными канала |
| DELETE | `/channels/{id}/subscription` | Отписаться, ответ с текущими данными канала |
| GET | `/channels/{id}/members?page=0&limit=100` | Подписчики и их роли |
| PUT | `/channels/{id}/members/{userId}` | `{role}` → назначить или снять администратора канала |
| POST | `/conversations/{id}/messages` | JSON `{text}` либо multipart `text` + `files`; ответ `201` |
| GET | `/conversations/{id}/messages` | История с параметрами `limit`, `beforeId` или `afterId` |
| DELETE | `/conversations/{id}/messages/{messageId}` | Удалить сообщение по правам роли; ответ — заглушка сообщения |
| GET | `/conversations/{id}/messages/search?q=текст&page=0&limit=20` | Поиск только в выбранном диалоге |
| GET | `/attachments/{id}` | Скачать файл с проверкой доступа к диалогу или каналу |
| GET | `/events` | Поток событий текущего пользователя |

Списки возвращают `{items: [...], hasMore: boolean}`. `limit` — от 1 до 100. Список диалогов отсортирован по последней активности; история по умолчанию — по убыванию ID. `beforeId` загружает старые сообщения, `afterId` — новые по возрастанию ID. При `hasMore=true` передайте ID последнего полученного сообщения в следующий запрос. Курсоры относятся к конкретному диалогу, `beforeId` и `afterId` нельзя передать одновременно. Поиск ограничен первыми 1000 результатами.

Группы и каналы используют те же маршруты `/conversations/{id}/messages` и `/conversations/{id}/messages/search` для публикаций, истории и поиска: в них передаётся ID переписки. В личном диалоге оба участника пишут и удаляют свои сообщения. В группе владелец управляет всеми ролями и удаляет любые сообщения; администратор пишет, удаляет любые сообщения и управляет обычными участниками и читателями; участник пишет и удаляет свои сообщения; читатель только читает. В канале владелец управляет администраторами, владелец и администраторы публикуют и удаляют сообщения, подписчики читают. Владелец не может покинуть свою группу или отписаться от своего канала в MVP. Создатель канала автоматически подписан; подписка добавляет канал в список и включает доставку новых публикаций через SSE.

Логин канала: 3–32 латинские буквы, цифры или `_`, хранится в нижнем регистре и уникален среди каналов. Название: 1–80 символов, описание: до 500 символов. Ответ канала содержит `id`, `username`, `title`, `description`, `owner`, `subscribed`, `viewerRole`, `subscriberCount`, `lastMessageId`, `lastMessageText`, `lastActivityAt`. Ответ группы содержит `id`, `title`, `owner`, `viewerRole`, `memberCount` и данные последнего сообщения.

Логин: 3–32 символа `a-z`, `0-9`, `_`, регистр не учитывается. Отображаемое имя: от 1 до 80 символов. Дата рождения необязательна, изменяется через `/users/me` и не включается в ответы о других пользователях. Ответы пользователя содержат `avatarId` (`null`, если фото нет); при замене изображения выдаётся новый ID. Поддерживаются JPEG и PNG до 5 МиБ и 4096 × 4096 пикселей. Пароль: минимум 8 символов и максимум 72 байта UTF-8; хранится только BCrypt-хеш. В первой версии выдаётся только access-токен: через час нужен повторный вход. Клиентский выход удаляет токен на устройстве; серверного отзыва отдельного токена и refresh-потока пока нет.

### Пример диалога в PowerShell

```powershell
$api = 'http://localhost:8080/api/v1'
$alice = Invoke-RestMethod "$api/auth/register" -Method Post -ContentType 'application/json' -Body (
    @{ username='alice'; displayName='Alice'; password='Alice-password-123!' } | ConvertTo-Json
)
$bob = Invoke-RestMethod "$api/auth/register" -Method Post -ContentType 'application/json' -Body (
    @{ username='bob'; displayName='Bob'; password='Bob-password-123!' } | ConvertTo-Json
)
$aliceHeaders = @{ Authorization = "Bearer $($alice.accessToken)" }
$bobHeaders = @{ Authorization = "Bearer $($bob.accessToken)" }
$dialog = Invoke-RestMethod "$api/conversations" -Method Post -Headers $aliceHeaders -ContentType 'application/json' -Body (
    @{ userId=$bob.user.id } | ConvertTo-Json
)
Invoke-RestMethod "$api/conversations/$($dialog.id)/messages" -Method Post -Headers $aliceHeaders -ContentType 'application/json' -Body (
    @{ text='Hello, Bob!' } | ConvertTo-Json
)
Invoke-RestMethod "$api/conversations/$($dialog.id)/messages" -Headers $bobHeaders
```

Если эти логины уже зарегистрированы, используйте `/auth/login` с логином и паролем.

### Вложения

До 5 файлов, до 10 МиБ на файл, до 4096 символов текста. Можно отправить только файлы. Пустое сообщение и пустые файлы отклоняются. Все файлы и сообщение сохраняются одной транзакцией: ошибка любого файла отменяет всю отправку.

Голосовые сообщения записываются кнопкой микрофона, прикрепляются как аудиовложение и отправляются обычной кнопкой отправки. Перед отправкой запись можно прослушать или удалить. Лимит записи — 2 минуты и 10 МиБ; в переписке доступен аудиоплеер. Веб-запись требует HTTPS или localhost и разрешения микрофона. Сервер сохраняет исходный формат без преобразования кодеков; воспроизведение зависит от поддержки формата на устройстве.

Пример загрузки через `curl.exe` после команд выше:

```powershell
curl.exe -X POST "$api/conversations/$($dialog.id)/messages" `
    -H "Authorization: Bearer $($alice.accessToken)" `
    -F 'text=Document' -F 'files=@C:/path/to/report.pdf'
```

Файлы хранятся в PostgreSQL (`bytea`); списки загружают только метаданные, без бинарного содержимого. Это упрощает транзакции и резервное копирование для учебного проекта, но увеличивает БД — при больших объёмах потребуется отдельное файловое/объектное хранилище. Имя очищается от компонентов пути и управляющих символов. При скачивании всегда выставляются `Content-Disposition: attachment`, `application/octet-stream`, `nosniff` и `no-store`; присланный клиентом MIME-тип не считается доверенным.

Веб-клиент показывает поддерживаемые браузером фото и видео внутри сообщений. Для отображения он загружает вложение с авторизацией и создаёт временный локальный Blob URL; токен в URL не попадает. Формат выбирается по разрешённому расширению, содержимое декодирует браузер. SVG и HTML не встраиваются. Видео воспроизводится стандартным плеером с управлением и без автозапуска. Скачать можно любое вложение; неподдерживаемый или повреждённый медиафайл остаётся доступен как файл. Антивирусная проверка пока не реализована.

### События в реальном времени

```powershell
curl.exe -N "$api/events" -H "Authorization: Bearer $($bob.accessToken)"
```

События:

- `ready`: соединение установлено; данные содержат `userId`.
- `message.created`: DTO нового сообщения, SSE `id` совпадает с ID сообщения.
- `message.deleted`: `{conversationId, messageId}`; текст и вложения удалённого сообщения недоступны, история возвращает заглушку с `deleted: true`.
- Каждые 20 секунд приходит комментарий heartbeat.

Событие отправляется участникам личного диалога или группы либо подписчикам канала только после коммита транзакции. Допускаются 5 одновременных подключений на пользователя. Соединение ограничено сроком действия JWT. В браузере используйте `fetch` со streaming body и заголовком Authorization: обычный `EventSource` не позволяет передать этот заголовок. Не передавайте JWT в URL.

SSE служит уведомлением, а PostgreSQL — источником истории. После события `ready` загрузите список диалогов и пропущенные сообщения через `afterId` для каждого диалога; объединяйте историю и события по ID без дубликатов. Сервер не воспроизводит события по `Last-Event-ID`. Сначала подключайтесь к SSE, затем синхронизируйте историю, чтобы закрыть промежуток между запросами.

### Поиск

Elasticsearch индексирует текст сообщения и ID диалога, но не содержимое вложений. Фоновая задача раз в 3 секунды обрабатывает до 100 сообщений с сохранённым в PostgreSQL признаком незавершённой индексации. При сбое данные остаются в БД, обработка повторяется; повторная запись использует тот же ID документа. При удалении индекса следующая задача создаст его и переиндексирует сообщения.

Новые сообщения появляются в поиске с задержкой индексации и обновления Elasticsearch. При недоступности поиска API возвращает `503`, обычная переписка продолжает работать. Поиск фильтруется по диалогу, права проверяются до обращения к Elasticsearch, результаты перечитываются из PostgreSQL.

## Проверки

Для текущего этапа групп и ролей прошли `mvn.cmd -q -DskipTests compile`, проверка TypeScript веба и мобильного клиента через локальный `tsc --noEmit`, а также сборка веб-клиента через локальный Vite. После запуска Docker Desktop образ backend собран, Flyway применил V4 к PostgreSQL 17, сервер стартовал, а OpenAPI опубликовал маршруты групп и ролей. Формальные тесты и проверка интерфейса на устройствах не выполнялись по запросу пользователя.

```powershell
.\mvnw.cmd test
.\mvnw.cmd verify -Pintegration
```

`mvn test` выполняет API-тесты с H2 в режиме PostgreSQL и той же миграцией Flyway, а также проверки JWT и конфигурации. `mvn verify -Pintegration` дополнительно запускает временные PostgreSQL 17 и Elasticsearch 9.2.8 через Testcontainers: проверяет API, реальный поиск, пересоздание индекса, повтор индексации после сбоя и одновременное открытие диалога. Для второй команды нужен Docker; контейнеры удаляются после тестов. H2 не заменяет проверку на PostgreSQL.

Проект рассчитан на один экземпляр бэкенда: соединения SSE находятся в памяти процесса. Для нескольких экземпляров потребуется доставка событий между ними. Редактирование сообщений, передача владения, отметки прочтения и push-уведомления не входят в текущий MVP.

## Структура

`auth`, `user`, `conversation`, `group`, `channel`, `message`, `attachment`, `search`, `realtime` — функциональные пакеты с отдельными контроллерами, сервисами и репозиториями. Общая конфигурация — `config`, ошибки и ответы списков — `common`. Группы и каналы переиспользуют сообщения, вложения, поиск и события переписки. Схема управляется только Flyway, Hibernate проверяет её при старте. Подключённые пользовательские скиллы находятся в `.agents/skills`.

Версии и соглашения проверены по [документации Spring Boot](https://docs.spring.io/spring-boot/4.0/appendix/dependency-versions/coordinates.html) и [springdoc-openapi](https://springdoc.org/).
