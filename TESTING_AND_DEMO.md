# Как проверить Minechat и показать преподавателю

Команды ниже — для PowerShell. Начинать из корня репозитория, где находятся README.md, pom.xml и compose.yaml. Нужны JDK 21, Node.js 24, pnpm и Docker Desktop в режиме Linux containers.

## 1. Выполнение требований

| Требование | Что сделано |
|---|---|
| Сайт, Desktop и Mobile | React, Electron, React Native / Expo |
| WebSocket | Получение новых сообщений и событий удаления во всех трёх клиентах |
| Личные чаты, группы, каналы | Создание, поиск, участники, подписки и роли |
| Файлы в переписке | Файлы, фото, видео и голосовые сообщения |
| Профиль | Отображаемое имя, дата рождения и аватар |
| Автотесты | Серверные, интеграционные и клиентские тесты |
| Docker | Сервер, сайт, PostgreSQL и Elasticsearch; отдельный стенд для нагрузки |
| GitHub и README с ФИО | Автор в README: Усачёв Марат Александрович |
| Нагрузочные тесты | Сценарий с разными пользователями и одновременными WS-соединениями |

Отправка сообщений и файлов выполняется через REST API, доставка событий — через WebSocket. Требование использовать WebSocket выполнено; весь API переводить на него не требуется. Старый SSE endpoint оставлен для совместимости, обновлённые клиенты его не используют.

Нативные приложения запускаются на компьютере и телефоне, а не внутри Docker. Успешная сборка не заменяет ручную проверку на устройстве. Новый транспорт нужно отдельно проверить на своём телефоне перед защитой; работа на iOS и сборка установщиков на всех ОС этой проверкой не подтверждаются.

## 2. Что проверяется автоматически

### Сервер

Из корня проекта:

```powershell
.\mvnw.cmd test
```

Проверяются регистрация, вход, JWT, ошибки доступа, личные переписки, ограничения сообщений и файлов, приватность вложений, профиль и обработка аватара, присутствие пользователей.

Отдельные WebSocket-тесты проверяют настоящее соединение с сервером: авторизацию, доставку в личные чаты, группы и каналы, удаление сообщений, запрет событий посторонним пользователям, неверный токен, срок соединения и ограничения числа подключений.

Последняя проверка серверного набора: 39 тестов прошли. Эти тесты используют H2 и не требуют вручную запущенного backend. Включены проверки редактирования своих сообщений, подписей и прав участников.

Запуск только серверных WebSocket-тестов:

```powershell
.\mvnw.cmd test '-Dtest=WebSocketApiTest,WebSocketEventServiceTest'
```

### Настоящие PostgreSQL и Elasticsearch

Запустить Docker Desktop и выполнить из корня:

```powershell
.\mvnw.cmd verify -Pintegration
```

Команда сначала выполняет обычные серверные тесты, затем интеграционные. Testcontainers сам создаёт временные PostgreSQL и Elasticsearch и удаляет свои контейнеры после завершения.

Проверяются работа API на PostgreSQL, поиск только в выбранной переписке, восстановление индекса Elasticsearch, повтор индексации после сбоя и одновременное создание одного диалога. Также проверяются редактирование и переиндексация текста, включая одновременную работу индексатора и редактора. Последняя отдельная проверка интеграционного набора: 16 тестов прошли.

Первый запуск занимает несколько минут: скачиваются и запускаются образы. Интеграционные тесты и нагрузку лучше выполнять последовательно, чтобы они не мешали друг другу.

### Веб и общий транспорт мобильного приложения

Из корня:

```powershell
cd frontend
pnpm install --frozen-lockfile
pnpm test
pnpm typecheck
pnpm lint
pnpm build
cd ..
```

Одиннадцать тестов проверяют формат WS-событий, порядок восстановления истории и доставки событий, неверные кадры, отмену соединения, закрытие во время восстановления, таймаут, совместимость AbortSignal с React Native, события редактирования и защиту свежих правок от старых ответов сервера.

Typecheck, lint и build — отдельные проверки типов, правил кода и сборки. Они не являются ручным тестированием интерфейса.

### Десктоп

Сначала установить зависимости frontend, как показано выше. Затем из корня:

```powershell
cd desktop
pnpm install --frozen-lockfile
pnpm test
cd ..
```

Команда собирает Electron и интерфейс, затем запускает два теста: передачу PUT-запроса профиля через прокси и ограничения WebSocket в CSP. Они не проверяют нажатия кнопок в настоящем окне Electron.

### Мобильное приложение

Из корня:

```powershell
cd mobile
pnpm install --frozen-lockfile
pnpm typecheck
cd ..
```

Это проверка TypeScript. Общий транспорт проверяется тестами frontend, но навигацию, клавиатуру, выбор файлов и запись голоса нужно проверить на телефоне через Expo Go.

## 3. Нагрузочный тест

Это отдельный локальный стенд с собственными базами и портом 18080. Он не использует рабочий сайт и не требует запускать обычный compose.yaml.

Из корня проекта:

```powershell
node loadtests/init.mjs
docker compose -p minechat-loadtest --env-file loadtests/.env -f compose.load.yaml up -d --build
```

Параметры и запуск:

```powershell
$env:LOAD_USERS = '100'
$env:LOAD_DURATION_SEC = '60'
$env:LOAD_MESSAGE_INTERVAL_MS = '5000'

docker compose -p minechat-loadtest --env-file loadtests/.env -f compose.load.yaml --profile test run --rm loadtest
```

| Переменная | Значение |
|---|---|
| LOAD_USERS | Число одновременных пользователей; чётное от 2 до 1000 |
| LOAD_DURATION_SEC | Длительность основной фазы в секундах, от 5 до 600 |
| LOAD_MESSAGE_INTERVAL_MS | Пауза между операциями пользователя в миллисекундах, от 250 до 60000 |

Например, для 200 пользователей на две минуты изменить LOAD_USERS на 200 и LOAD_DURATION_SEC на 120. При сохранённой паузе 5000 нагрузка от каждого пользователя останется примерно той же, а подключений станет больше.

100 пользователей — это не 100 запросов в секунду. Частота зависит от паузы и времени ответа. Начать можно с 10 пользователей, затем проверить 50, 100 и 200. То, что скрипт допускает 1000, не означает, что компьютер или сервер выдержит такую нагрузку.

### Если нужно несколько прогонов

После запуска стенда и задания переменных выполнить из корня:

```powershell
for ($run = 1; $run -le 3; $run++) {
    docker compose -p minechat-loadtest --env-file loadtests/.env -f compose.load.yaml --profile test run --rm loadtest
    $code = $LASTEXITCODE
    Copy-Item target/load-results/latest.json "target/load-results/run-$run.json"
    if ($code -ne 0) { throw "Прогон $run не прошёл, смотри отчёт" }
}
```

Это три прогона. Для пяти заменить 3 на 5. Каждый прогон создаёт новые тестовые аккаунты; результаты остаются отдельными файлами. Переменные PowerShell сохраняются в этом терминале, поэтому перед следующим запуском явно задать нужные значения.

### Что делает нагрузочный сценарий

1. Создаёт отдельный аккаунт каждому пользователю и выполняет вход.
2. Разбивает пользователей на пары и создаёт личные переписки.
3. Открывает отдельное авторизованное WebSocket-соединение каждому пользователю.
4. Отправляет сообщения через REST и получает их на стороне собеседника через WS.
5. Читает историю и проверяет отправленное сообщение.
6. Считает ошибки, время ответов, доставку, разрывы и события из чужих переписок.

Нагрузка проверяет именно этот сценарий личных переписок. Она не измеряет массовую загрузку видео, звонки, все экраны интерфейса или предельную ёмкость сервера.

### Как прочитать результат

Отчёт: target/load-results/latest.json. После запуска можно посмотреть:

```powershell
Get-Content target/load-results/latest.json
```

- passed: true — все заданные условия прошли
- workloadHttp.failed — число неуспешных запросов основной фазы
- workloadHttp.p95Ms — время, в которое уложились 95% HTTP-запросов
- websocket.deliveryRate — доля доставленных сообщений; 1 означает 100%
- websocket.deliveryP95Ms — время доставки для 95% сообщений
- websocket.peakConnections — максимум одновременных соединений
- checks — результаты отдельных проверок

Код выхода 0 означает успех, 1 — ошибки или превышение порогов. Регистрация и вход учитываются отдельно в setupHttp. По умолчанию допускается не больше 1% HTTP-ошибок, P95 HTTP и доставки до 2000 мс, доставка не меньше 99%, без разрывов и утечек событий.

Контрольный локальный прогон: 100 пользователей, 2556 HTTP-запросов без ошибок, 1278 из 1278 сообщений доставлены. P95 HTTP — 115,30 мс, доставки — 241,33 мс. Условия и результаты: [loadtests/RESULTS.md](loadtests/RESULTS.md). Эти цифры не подтверждают такую же производительность VM в Yandex Cloud.

Остановить только нагрузочный стенд, сохранив его данные:

```powershell
docker compose -p minechat-loadtest --env-file loadtests/.env -f compose.load.yaml down
```

## 4. Показ преподавателю

### Подготовить заранее

1. Проверить сайт, вход в Electron и Expo Go на своём телефоне.
2. Во всех трёх клиентах использовать один backend. Для облачного сервера в desktop/.env указать MSRPO_BACKEND_URL=https://84.201.180.177.sslip.io, в mobile/.env — EXPO_PUBLIC_API_URL=https://84.201.180.177.sslip.io/api/v1. После изменения перезапустить клиенты.
3. Подготовить два демонстрационных аккаунта, например А и Б. На сайте войти как А, в Electron — как Б, на телефоне — как А.
4. Подготовить небольшие фото, видео и PDF. Проверить разрешение микрофона.
5. Открыть GitHub, README с ФИО и результаты тестов.

Аккаунты локального backend и облачного сервера — разные. Для показа обмена сообщениями все клиенты должны смотреть на один сервер.

### Сценарий на 5–10 минут

1. **Три клиента.** Показать сайт, отдельное окно Electron и приложение на телефоне. Объяснить: интерфейсы разные, сервер и аккаунты общие.
2. **Личный чат.** Найти аккаунт Б по логину. Отправить сообщения с сайта, из Electron и с телефона. Показать появление сообщений без обновления страницы.
3. **WebSocket.** В браузере открыть инструменты разработчика → Network → WS. Показать соединение /api/v1/ws со статусом 101 и события message.created. Первый auth-кадр содержит токен: для демонстрации выбрать кадр с сообщением.
4. **Группа.** Создать группу и добавить Б. Написать сообщение с обоих аккаунтов. Показать участников и роли; для читателя отправка недоступна.
5. **Канал.** Создать канал от А, найти его от Б, подписаться и показать публикации. Объяснить: публикуют владелец и администраторы, подписчики читают.
6. **Вложения и действия.** Отправить фото, видео, PDF и короткое голосовое. Фото и видео видны внутри чата, PDF можно скачать. Имена фото и видео не выводятся. Правой кнопкой мыши или долгим нажатием открыть меню, изменить свою подпись, показать отметку «изменено» и скачать выбранное фото. Чужой текст редактировать нельзя.
7. **Профиль.** Изменить отображаемое имя, загрузить аватар и указать дату рождения. Показать сохранение. Дата рождения доступна только владельцу.
8. **Поиск.** Отправить уникальную фразу и найти её через поиск сообщений. Индексации Elasticsearch может потребоваться несколько секунд.
9. **Docker.** Показать compose.prod.yaml: сайт, backend, PostgreSQL, Elasticsearch. В терминале VM из ~/minechat показать контейнеры командой ниже. Десктоп и мобильное приложение работают на устройствах.
10. **Тесты.** Запустить серверные и клиентские тесты. Показать результат интеграционных тестов и нагрузочный отчёт. Если позволяет время, выполнить нагрузку на 10–100 пользователей; подготовка стенда идёт отдельно от минутной нагрузки.
11. **GitHub.** Показать репозиторий, README с ФИО и GitHub Actions с результатом деплоя.

Команда для показа контейнеров на VM:

```sh
cd ~/minechat
sudo docker compose -p minechat-prod --env-file .env.prod -f compose.prod.yaml ps
```

На защите не обязательно заново собирать все образы и ждать интеграционные тесты. Подготовить окружение заранее, показать сохранённые результаты и при необходимости повторить выбранную проверку.

## 5. Проверка размещённой версии в Yandex Cloud

Адрес: https://84.201.180.177.sslip.io. На сайте, в Electron и на телефоне выбрать этот же сервер, как описано выше.

### Проверка доступности

В PowerShell:

```powershell
curl.exe -sS -o NUL -w "%{http_code}\n" https://84.201.180.177.sslip.io/
curl.exe -sS -o NUL -w "%{http_code}\n" https://84.201.180.177.sslip.io/api/v1/users/me
```

Первый ответ должен быть 200, второй — 401. Ответ 401 здесь ожидаемый: сервер работает и не отдаёт профиль без входа. Это проверка доступности, а не проверка всех функций.

### Проверка функций на сервере

1. Создать два демонстрационных аккаунта на размещённом сайте. Открыть один в обычном окне браузера, другой — в инкогнито или Electron.
2. Найти друг друга и отправить сообщения в обе стороны. Проверить, что сообщения появляются без обновления страницы.
3. Открыть Network → WS и проверить /api/v1/ws: должен быть статус 101 и события ready, message.created. После переключения вкладки в офлайн и возврата в сеть проверить, что пропущенные сообщения появились.
4. Загрузить небольшие фото, видео и PDF; открыть или скачать их со второго аккаунта. Проверить удаление своего сообщения.
5. Создать группу и канал, добавить или подписать второй аккаунт, проверить отправку и ограничения ролей.
6. Изменить профиль: имя, дату рождения и аватар. Войти этим аккаунтом на телефоне и проверить сохранённые данные.
7. Найти отправленную фразу в поиске сообщений. Из-за индексации результат может появиться с задержкой.

Демонстрационные аккаунты и переписки останутся на рабочем сервере. Использовать вымышленные данные.

### Проверка контейнеров и логов на VM

После подключения по SSH выполнить в ~/minechat:

```sh
sudo docker compose -p minechat-prod --env-file .env.prod -f compose.prod.yaml ps
sudo docker compose -p minechat-prod --env-file .env.prod -f compose.prod.yaml logs --tail=100 backend web
```

В списке должны работать web, backend, postgres и elasticsearch. При проблемах проверить логи, затем сопоставить результат с GitHub Actions. Успешный деплой подтверждает запуск контейнеров и ответ API, но сам по себе не проверяет все действия пользователя.

### Какие автотесты относятся к облаку

Команды mvnw test, mvnw verify -Pintegration и pnpm test выполняются локально или в окружении запуска тестов. Они не проверяют автоматически размещённый сайт по его URL.

По умолчанию loadtests/run.mjs запрещает публичные адреса. Для больших облачных нагрузок нужен отдельный тестовый стенд с собственной базой. Согласованный ограниченный прогон рабочего сайта описан в следующем разделе. Локальные результаты RESULTS.md не являются результатами нагрузочного теста облачной VM.

## 6. Нагрузка именно на рабочий сайт

Этот режим добавлен отдельно после согласования проверки рабочего сервера. Он создаёт тестовые аккаунты и переписки в облачной базе. Для первого прогона ограничение — 10 пользователей, 60 секунд и пауза не меньше 5000 мс. При ошибке запроса основной фазы или разрыве WS проверка останавливается, нагрузка не увеличивается.

Генератор запускается на компьютере, Docker для этого прогона не нужен. Так измеряются публичный HTTPS API, доставка через WSS и сеть между компьютером и Yandex Cloud.

Из корня проекта в PowerShell:

```powershell
$env:ALLOW_REMOTE_LOAD = '1'
$env:BASE_URL = 'https://84.201.180.177.sslip.io/api/v1'
$env:USERS = '10'
$env:DURATION_SEC = '60'
$env:MESSAGE_INTERVAL_MS = '5000'
$env:REPORT_PATH = 'target/load-results/cloud-10.json'

node loadtests/run.mjs --check-config
node loadtests/run.mjs
```

Первая команда только проверяет параметры, без запросов. Вторая выполняет нагрузку. Без ALLOW_REMOTE_LOAD=1 публичные адреса заблокированы. Повышать число пользователей сверх 10 в этом режиме пока нельзя: для этого нужно отдельно согласовать следующий уровень нагрузки.

Во время теста на VM в другом терминале можно посмотреть ресурсы:

```sh
sudo docker stats --no-stream
```

После теста открыть отчёт:

```powershell
Get-Content target/load-results/cloud-10.json
```

Он отличается от локального отчёта latest.json: runMode будет cloud, target — адрес рабочего сайта. Аккаунты и тестовые сообщения после прогона останутся на сервере. Для дальнейших больших нагрузок использовать отдельную облачную копию с собственной базой.

Вернуть терминал к локальному режиму:

```powershell
Remove-Item Env:ALLOW_REMOTE_LOAD -ErrorAction SilentlyContinue
Remove-Item Env:BASE_URL -ErrorAction SilentlyContinue
Remove-Item Env:REPORT_PATH -ErrorAction SilentlyContinue
$env:USERS = '100'
```
